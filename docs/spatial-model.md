# 공간 데이터 모델 — 위에서 본 링과 두 개의 원

작성일: 2026-07-28
상태: 설계 확정, 구현 전

이 문서는 **복싱 공간 데이터를 어떤 형태로 만들 것인가**를 정한다.
개념은 `docs/spatial-primer.md`, 계획은 `docs/spatial-project.md` 를 본다.

## 결정 1 — 위에서 본 링으로 투영한다

영상에서 뽑은 데이터를 **링을 바로 위에서 내려다본 2D 좌표**로 바꾼다.
지표를 따로따로 계산하지 않고, 먼저 이 표현을 만든 다음 거기서 전부 유도한다.

### 왜 이 방식인가

**복싱의 공간이 실제로 2D다.** 두 선수 다 바닥 위에 서 있다. 높이는 거의 무의미하다.
2D 평면은 정보를 버리는 게 아니라 **딱 맞는 표현**이다. 축구 분석이 같은 이유로
top-down 을 쓴다.

**네 층이 하나의 표현에 전부 담긴다.**

| 층 | 위에서 본 그림에서 |
|---|---|
| 거리 | 두 점 사이 간격 |
| 움직임 | 점의 시간 변화 |
| 링 | 점의 절대 위치 |
| 각도 | 점에 붙은 화살표 |

따로 계산할 게 없다. 좌표 하나에서 전부 나온다.

**눈으로 검증된다.** 1단계에서 확인용 영상을 눈으로 보는 것이 가장 강력한 검증
수단이었다. 위에서 본 그림은 그 자체가 검증 도구다. 두 점이 링 안에서 말이 되게
움직이는지 보면 바로 안다.

**도메인 언어와 일치한다.** "코너로 몬다", "중앙을 잡는다", "부채꼴로 좁힌다" —
전부 위에서 본 그림이다. 코치가 화이트보드에 그리는 게 top-down 이다.
표현이 도메인 사고방식과 같으면 결과를 해석하기 쉽다.

### 검토한 대안

| 방식 | 왜 안 쓰나 |
|---|---|
| 화면 좌표 그대로 | 원근 왜곡. 카메라 각도가 다르면 **영상 간 비교가 안 된다** |
| 거리 스칼라 하나만 | "어디서" 그 거리였는지가 사라진다. 링 층이 통째로 날아간다 |
| 3D 자세 복원 | 카메라 한 대로는 깊이가 불안정하고, **필요 없는 정보가 대부분**이다. 팔꿈치 각도는 공간 분석에 쓸 데가 없다 |
| 영상을 통째로 학습 | 라벨이 수천 개 필요하고, **왜 그렇게 판단했는지 설명이 안 된다.** 목적이 이해인데 이해를 주지 않는다 |

### top-down 이 못 담는 것

동의만 하고 넘어가지 않기 위해 한계도 적어둔다. 셋 다 **top-down 을 대체하는 게
아니라 위에 얹는 것들**이다.

| 한계 | 대응 |
|---|---|
| 높이 — 더킹·슬리핑이 안 보인다 | 점에 "지금 얼마나 낮은지" 를 값으로 붙인다 |
| 팔 상태 — 뻗은 팔과 접은 팔은 사거리가 다르다 | 마찬가지로 값으로 붙인다 |
| 겹칠 때 부정확 — 발 위치가 흔들린다 | 신뢰도를 같이 기록한다. 1단계에서 이미 하고 있다 |

## 결정 2 — 선수를 원 두 개로 표현한다

각 선수는 점 하나가 아니라 **동심원 두 개**다.

```
        ╭─────────────╮
       ╱   ╭───────╮   ╲
      │   │  몸 원  │    │  ← 사거리 원
      │    ╰───────╯    │
       ╲               ╱
        ╰─────────────╯
```

| 원 | 뜻 |
|---|---|
| **몸 원** | 몸이 차지하는 공간 |
| **사거리 원** | 팔을 뻗어 닿는 범위 |

### 5단계 거리가 원 관계에서 자동으로 나온다

`docs/spatial-primer.md` 2장의 거리 5단계를 **주관적 판단 없이** 얻을 수 있다.

```
① 아웃 오브 레인지         ② 엣지 오브 레인지
   (  A  )    (  B  )        (  A  )(  B  )
   사거리 원이 안 닿음        사거리 원이 딱 닿음

③ 롱 레인지                ④ 미드 · 클로스
   (  A ( ) B  )              ( A(X)B )
   사거리 원이 상대 몸에 닿음   몸 원까지 가까움
```

| 단계 | 원의 관계 |
|---|---|
| 아웃 오브 레인지 | 사거리 원끼리 안 닿음 |
| **엣지 오브 레인지** | **사거리 원이 서로 닿는 순간** |
| 롱 레인지 | 내 사거리 원이 상대 **몸 원**에 닿음 |
| 미드 레인지 | 겹침이 커짐 |
| 클로스 레인지 | 몸 원이 거의 닿음 |

**이게 중요한 이유**: 1단계에서 밀착 경계를 0.65m 로 정할 때는 사진을 보고
사람이 판단했다. 주관적이었다. 원 방식은 **"닿나 안 닿나"** 라는 객관적 기준을 준다.

### 리치 차이가 자동으로 담긴다

두 선수의 사거리 원 크기가 다르면 **한쪽만 닿는 구간**이 생긴다.

```
     ┌────── A의 사거리 (김) ──────┐
   ( A )                        ( B )
              └── B의 사거리 (짧음) ──┘
     └────┘
      A만 닿는 구간
```

primer 1장에서 말한 그 구간이다. 리치가 짧은 쪽에게는 지옥이고, 긴 쪽은 상대를
여기 붙잡아두려 한다. **거리 하나만 재서는 절대 안 나오는 정보다.**

여기서 바로 나오는 스탯 세 개:

| 스탯 | 정의 |
|---|---|
| **일방 우위 시간** | 내 사거리 안 + 상대 사거리 밖 |
| **동시 위험 시간** | 둘 다 닿음 |
| **안전 시간** | 둘 다 못 닿음 |

이 셋만으로 스타일이 상당 부분 설명된다. 아웃복서는 일방 우위 시간이 길고,
스워머는 동시 위험 구간을 통과해 들어가는 사람이다.

### 원은 앞쪽으로 치우친다

복서는 등 뒤를 때리지 못한다. 실제 사거리는 정면 쪽으로 쏠려 있다.

```
   정면 →
     (  (    ))
   뒤는 짧고 앞은 길다
```

원을 정면 방향으로 치우친 모양으로 두면 **각도가 같은 그림에 들어온다.**
"같은 거리인데 옆을 잡혔다" 가 **원이 안 겹치는 상태**로 표현된다.
각도가 별도 층이 아니게 된다.

### 사거리 반경을 어떻게 정하나

| 방법 | 장점 | 단점 |
|---|---|---|
| 키에서 비율로 추정 | 항상 계산됨 | 사람마다 팔 비율이 다름 |
| 자세 모델의 어깨~손목 (매 프레임) | 실측값 | 팔 접으면 짧게 나오고, 카메라 쪽으로 뻗으면 왜곡 |
| **영상 전체에서 최대치** | **안정적. 선수별 상수가 됨** | 최대로 뻗은 순간이 영상에 있어야 함 |

**세 번째를 쓴다.** 자세 모델이 어깨·팔꿈치·손목을 주므로 계산은 쉽고,
스파링이면 최대로 뻗는 순간이 반드시 나온다.

> **나중에**: 잽 사거리와 훅 사거리는 다르다. 원이 여러 개여야 정확하다.
> 하지만 그건 2단계(펀치 검출)가 있어야 알 수 있다. 지금은 하나로 시작한다.

## 결정 3 — 데이터 형태

프레임마다, 선수마다 한 줄.

```
frame          프레임 번호
time_sec       시간
fighter        me / opponent

x, y           링 위 위치 (링 좌표)
facing         정면 방향 (각도)
body_r         몸 반경
reach_r        사거리 반경
crouch         얼마나 낮췄나        ← 2차
arm_extend     팔을 얼마나 뻗었나    ← 2차
confidence     이 줄을 믿을 수 있나
```

여기서 파생되는 모든 값(거리, 속도, 링 위치, 각도 우위, 사거리 겹침)은
**계산해서 얻는 것이지 따로 측정하는 게 아니다.**

## 결정 4 — 링 경계는 처음부터 넣는다

링 좌표를 만들려면 **화면 속 링의 네 모서리**가 필요하다.
이 대응만 알면 화면의 아무 점이나 링 좌표로 바꿀 수 있다 (호모그래피).

즉 **"링을 인식한다" = "캔버스 네 모서리를 찾는다"** 이다.

### 이건 이미 풀린 문제다

축구 방송 분석에서 **sports field registration(경기장 정합)** 이라는 이름으로
잘 정리돼 있다.

| 자료 | 내용 |
|---|---|
| [Roboflow 튜토리얼](https://blog.roboflow.com/camera-calibration-sports-computer-vision/) | YOLO 키포인트로 표식을 찾아 호모그래피 계산. 가장 실용적 |
| [TVCalib](https://arxiv.org/abs/2207.11709) | 연구급. 카메라 자세와 초점거리를 같이 추정 |
| [Football-PitchVision](https://github.com/DesusLove/Football-PitchVision) | 검출 → 추적 → 호모그래피 → top-down 레이더 전체 파이프라인 |
| [SoccerNet Game State Reconstruction](https://arxiv.org/pdf/2404.11335) | 미니맵 복원을 벤치마크로 정의 |

축구용이라 모델은 그대로 못 쓰지만 **파이프라인 구조가 같다.**

### 복싱 링이 오히려 유리하다

| | 축구장 | 복싱 링 |
|---|---|---|
| 표식 | 선·원·박스, 많지만 복잡 | **정사각형 하나** |
| 필요한 점 | 여러 개 조합 | **모서리 4개면 끝** |
| 가려짐 | 선수가 선을 가림 | **로프는 항상 선수 앞에 있다** |

### 화면 밖 모서리 문제는 풀린다

우리 영상(`IMG_0711`)은 링 앞쪽 두 모서리가 화면 밖이라 막혀 있었다.

**모서리를 직접 찾는 대신 로프·캔버스 경계선을 찾아 연장한다.**
두 선이 만나는 점이 모서리이고, 그 점이 화면 밖이어도 계산으로 구할 수 있다.

```
   경계선 1 ─────────────╲
                          ╲
                           ╳  ← 화면 밖 모서리도 구해짐
   경계선 2 ──────────────╱
```

**다시 찍지 않아도 3층이 열린다.**

### 난이도가 두 갈래로 갈린다

| | 고정 카메라 (우리 영상) | 중계 영상 |
|---|---|---|
| 모서리 찾기 | **영상당 한 번** | **매 프레임** |
| 방법 | 손으로 4점 | 자동 검출 모델 |
| 비용 | 몇 분 | 진짜 작업 |

카메라가 고정이면 링이 안 움직이므로 한 번 찍어두면 영상 전체에 쓴다.

**그래서 고정 카메라부터 한다.** 두 가지 위험을 분리하기 위해서다.

1. top-down 분석이 실제로 쓸모 있나?
2. 카메라 자동 정합이 되나?

고정 카메라에서는 1번만 검증하면 된다. 여기서 쓸모가 확인돼야 2번에 투자할
근거가 생긴다. 반대로 하면 자동 검출을 다 만들고 나서 분석이 별로일 수 있다.

**부수 효과**: 손으로 찍은 결과가 자동 검출의 **정답지**가 된다.
같은 영상에 자동 검출을 돌려 비교하면 정확도를 바로 잴 수 있다.

## 결정 5 — 스탯이 먼저, 분류는 나중

스타일 4분류를 목적지로 삼지 않는다. **스탯을 만드는 것이 목적**이고,
스타일 분류는 그 위에서 할 수 있는 여러 가지 중 하나다.

이유:

- 스탯이 있으면 스타일 분류도, 특정 라운드 분석도, 매치업 분석도, 본인 코칭도 된다
- **스탯은 하나씩 눈으로 검증할 수 있다.** 군집은 검증이 어렵다
- 야구 세이버메트릭스가 이 순서였다. 먼저 스탯을 만들고, 유형 논의는 그 다음이었다

### 나올 수 있는 스탯들

| 층 | 스탯 |
|---|---|
| 거리 | 5단계별 체류 시간, 일방 우위 / 동시 위험 / 안전 시간 |
| 움직임 | 접근 주도 비율, 후퇴 주도 비율, 전진·후퇴 시간 비 |
| 링 | 중앙 점유율, 로프·코너 압박 시간, 갈 수 있는 방향의 각도 범위 |
| 각도 | 각도 우위 시간, 피벗 빈도 |

## 단계

1. **링 4점을 손으로 찍어 top-down 뷰 만들기** — 지금 데이터로 바로 된다
2. **사거리 반경 뽑기** — 자세 모델의 어깨~손목 최대치. 5단계가 깔끔히 갈리는지 확인
3. **정면 방향 추가** — 어깨 좌표에서. 원을 앞쪽으로 치우치게
4. **스탯 계산** — 위 표의 값들
5. **중계 영상용 자동 정합** — 여기부터가 큰 작업

1번과 2번이 이 설계 전체의 시험대다. 여기서 그림이 말이 되면 나머지는 따라온다.
